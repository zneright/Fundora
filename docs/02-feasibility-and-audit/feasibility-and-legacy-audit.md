## 1. Executive Summary of the Legacy Audit

An independent, line-by-line source code inspection of [`barangay-bond`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/README.md) confirmed that the legacy application contains rich, domain-specific civic governance workflows tailored for Philippine **Sangguniang Kabataan (SK)** and **Barangay** project accountability. However, the inspection also verified **all 12 critical legacy issues** across the smart contract, wallet management, Firestore security rules, AI integration, and ledger indexing layers.

This document records the exact source-code evidence for each legacy defect, defines the remediation strategy for **Fundora**, establishes the **Feature Disposition Matrix** (`Preserve`, `Redesign`, `Simplify`, `Defer`, `Remove`), and finalizes the **NEAR Hackathon 2026 Track Alignment**.

## 2. Source-Verified Evidence of the 12 Critical Legacy Issues

### Issue 1: Plaintext Stellar Private Keys Stored in Firestore User Documents
- **Legacy Evidence:** In [`src/services/inAppWallet.service.ts`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/services/inAppWallet.service.ts#L62-L71), `provisionInAppWallet()` generates a Stellar keypair using `Keypair.random()` and writes `inAppWalletSecret: secretKey` (plaintext `S...` private key) directly into `users/{uid}` in Firestore. When signing transactions (`signWithInAppWallet`, [`inAppWallet.service.ts`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/services/inAppWallet.service.ts#L106-L133)), the client fetches `userSnap.data().inAppWalletSecret` into browser memory.
- **Compound Vulnerability:** Because [`firestore.rules`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/firestore.rules#L96) sets `allow list: if isAuthenticated();` on `/users/{userId}`, any logged-in user can query the `users` collection and steal every user's plaintext private key, including the Barangay Admin's and SK Officials' wallets.
- **Fundora Remediation:** **Permanently remove `inAppWallet.service.ts` and `inAppWalletSecret`.** All wallet connections use **NEAR Wallet Selector** (`@near-wallet-selector/core`) where private keys remain inside the user's non-custodial wallet (MyNearWallet, Meteor Wallet, Here Wallet), optionally paired with scoped **Function-Call Access Keys** stored only in browser `localStorage` and bound strictly to the Fundora contract address.

### Issue 2: Overly Permissive and Conflicting Firestore Security Rules
- **Legacy Evidence:** [`firestore.rules`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/firestore.rules) contains two severe flaws:
  1. Line 96 (`allow list: if isAuthenticated();` on `/users/{userId}`) exposes all user PII and secret keys to any authenticated account.
  2. Lines 464–505 ([`firestore.rules`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/firestore.rules#L464-L505)) define duplicate `match` blocks for `/notifications/{notifId}`, `/audit_logs/{logId}`, `/barangays/{barangayId}`, `/sessions/{sessionId}`, and `/barangay_admin_requests/{reqId}` that override the stricter rules defined earlier at lines 237–341. Because Firestore evaluates `OR` across matching blocks, `/audit_logs` becomes readable and writable by any authenticated user (`L472`), and `/mail/{mailId}` allows unauthenticated creation (`allow create: if true;` at `L459`).
- **Fundora Remediation:** Consolidate all rules into a single, non-overlapping [`firestore.rules`](file:///C:/Users/Renz%20Jericho%20Buday/Fundora/docs/06-database-design/database-and-data-model.md) specification. Separate public profile summaries from private PII/verification documents, scope `list` queries by `barangayId` and role, and restrict `ai_audit_records` and `verification_records` writes to the backend Firebase Admin SDK.

### Issue 3: Insecure On-Chain Voter Eligibility Checks
- **Legacy Evidence:** In [`contracts/contracts/barangay-bond/src/lib.rs`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/contracts/contracts/barangay-bond/src/lib.rs#L300), `vote_milestone` checks resident eligibility using:
  ```rust
  let is_youth: bool = env.storage().persistent().get(&voter_key).unwrap_or(true);
  ```
  Because `.unwrap_or(true)` defaults missing keys to `true`, **any arbitrary wallet address on the network** that was never registered or verified can vote on milestones. Additionally, `create_project` ([`lib.rs`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/contracts/contracts/barangay-bond/src/lib.rs#L137-L245)) never checks `DataKey::IsSK(sk_official)`.
- **Fundora Remediation:** In the Fundora NEAR Rust contract, voter eligibility defaults strictly to `false`. `vote_milestone` requires the caller (`env::predecessor_account_id()`) to be explicitly registered in `verified_residents` for the project's specific `barangay_id` (`assert_verified_resident(&barangay_id, &caller)`), and `create_project` verifies that `sk_official` is an active, registered SK Official in that same `barangay_id`.

### Issue 4: Incorrect / Hardcoded 1-Vote Quorum Behavior
- **Legacy Evidence:** In [`lib.rs`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/contracts/contracts/barangay-bond/src/lib.rs#L357-L377), `vote_milestone` hardcodes:
  ```rust
  if milestone.votes_approve >= 1 { ... }
  else if milestone.votes_reject >= 1 { ... }
  ```
  with the comment `// Threshold = 1 for instant single-resident testing`. Meanwhile, [`YouthDashboard.tsx`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/components/YouthDashboard.tsx#L251) misleads users by displaying `"Needs 60% votes to approve"`. A single vote immediately triggers payout or permanent rejection.
- **Fundora Remediation:** Store `quorum_bps: u16` (e.g., `6000` = 60% approval ratio) and `min_votes: u32` (minimum total votes required before quorum can resolve, e.g., $\ge 3$ in production barangays, or configurable `demo_mode: bool` scoped strictly to the isolated demo barangay `brgy-demo.fundora`) in the on-chain `BarangayConfig` and `Project` structs. Display the exact on-chain `min_votes` and `quorum_bps` dynamically in the UI.

### Issue 5: Refunds Routed to Inappropriate Recipients & Unwired in UI
- **Legacy Evidence:** In [`lib.rs`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/contracts/contracts/barangay-bond/src/lib.rs#L419-L458), `refund_project` requires `project.creator.require_auth()` (the SK Official) and transfers the remaining locked escrow funds (`token_client.transfer(&env.current_contract_address(), &project.creator, &remaining)`) **to the SK Official whose milestone was rejected**, instead of returning the funds to the Barangay Admin / Treasury that funded the escrow! Furthermore, [`refundProject`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/transactions/transactions.ts#L269-L280) is never called anywhere in the frontend.
- **Fundora Remediation:** Record `funder_treasury: AccountId` (the Barangay Admin treasury account that locked the NEAR funds) on every `Project` struct. When a milestone is rejected or a project is cancelled via `refund_project`, the NEAR smart contract transfers `remaining_balance` strictly back to `project.funder_treasury` and emits a `project_refunded` NEP-297 event. Wire the `"Reclaim Rejected Escrow to Treasury"` button directly into `AdminPanel`.

### Issue 6: Stale and Failing Smart Contract Unit Tests
- **Legacy Evidence:** In [`contracts/contracts/barangay-bond/src/test.rs`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/contracts/contracts/barangay-bond/src/test.rs#L51-L294), every test calls `client.create_project(...)` with 6 arguments instead of the 7 arguments required by [`lib.rs`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/contracts/contracts/barangay-bond/src/lib.rs#L145) (`immediate_phase_1: bool`), preventing compilation. Moreover, lines 89–97 of `test.rs` assert a 2-vote quorum that no longer matches the 1-vote logic in `lib.rs`.
- **Fundora Remediation:** Write a comprehensive Rust unit test suite (`#[cfg(test)]`) and `near-workspaces` sandbox integration test suite for the Fundora contract, enforcing CI checks so contract signatures and tests never drift.

### Issue 7: Single Global Administrator Model On-Chain
- **Legacy Evidence:** [`lib.rs`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/contracts/contracts/barangay-bond/src/lib.rs#L6-L15) defines a single global `DataKey::Admin` initialized once ([`lib.rs`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/contracts/contracts/barangay-bond/src/lib.rs#L102-L109)). While Firestore supports multiple barangays (`barangays/{id}`), on-chain permissions (`verify_youth`, `set_sk_official`, `create_project`) only check the single global `Admin` address.
- **Fundora Remediation:** Design a multi-tenant jurisdiction architecture on NEAR (`LookupMap<BarangayId, BarangayConfig>`), where `SystemAdmin` registers and activates a `BarangayId` (bound to its official PSGC code) and assigns one or more scoped `BarangayAdmin` NEAR accounts (`admin_accounts: UnorderedSet<AccountId>`) who exclusively manage that barangay's SK officials, verified residents, and project escrows.

### Issue 8: Client-Side Gemini API Credentials
- **Legacy Evidence:** [`src/services/gemini.ts`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/services/gemini.ts#L217) and [`src/services/aiProposalAdvisor.service.ts`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/services/aiProposalAdvisor.service.ts#L55) read `import.meta.env.VITE_GEMINI_API_KEY` and call `https://generativelanguage.googleapis.com/v1beta/...` directly from the client browser, exposing the API key in the production JavaScript bundle and DevTools network tab.
- **Fundora Remediation:** Remove `VITE_GEMINI_API_KEY` from the frontend environment completely. All Gemini 2.5 Flash requests are routed through authenticated backend endpoints (`/api/ai/verify-identity`, `/api/ai/audit-proposal`, `/api/ai/audit-evidence`) using server-only environment variable `GEMINI_API_KEY`.

### Issue 9: Client-Trusted AI Audit Results
- **Legacy Evidence:** Both identity OCR verification ([`verification.service.ts`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/services/verification.service.ts#L113-L314)) and proposal procurement audits ([`SKWorkspace.tsx`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/components/SKWorkspace.tsx#L163-L241)) run inside the user's browser and write the resulting confidence/feasibility scores directly to Firestore (`users`, `ai_verifications`, `proposals`). A malicious user can intercept the client call or write `aiFeasibilityScore: 100` directly via the Firestore SDK.
- **Fundora Remediation:** The backend AI Auditor service executes the Gemini evaluation, validates the structured JSON output, writes the immutable record to Firestore (`ai_audit_records`, protected against client writes in `firestore.rules`), and signs an on-chain attestation transaction (`record_ai_attestation`) on NEAR using the dedicated `auditor.fundora.testnet` keypair.

### Issue 10: Fragile Metadata-to-Blockchain Project Identification
- **Legacy Evidence:** In [`AdminPanel.tsx`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/components/AdminPanel.tsx#L431-L436), after calling `createProject()`, the client makes a separate RPC call `onChainProjectId = await getProjectCount()` to guess the newly created project's ID, and UI components ([`AdminPanel.tsx`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/components/AdminPanel.tsx#L1270-L1273), [`SKWorkspace.tsx`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/components/SKWorkspace.tsx#L278-L283), [`YouthDashboard.tsx`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/components/YouthDashboard.tsx#L94-L99)) fall back to matching projects by `p.name.toLowerCase() === prop.projectName.toLowerCase()`.
- **Fundora Remediation:** Use a deterministic, pre-generated UUID/slug (`project_id: String`, e.g., `"proj_137602003_2026_001"` or the Firestore proposal document ID) passed directly into the NEAR contract's `create_project(project_id, ...)` method. The contract enforces uniqueness (`assert!(!self.projects.contains_key(&project_id))`) and emits the exact `project_id` in its NEP-297 event log, eliminating race conditions and name-matching fallbacks.

### Issue 11: Hardcoded or Fabricated Transaction History Values
- **Legacy Evidence:** [`src/services/walletTransaction.service.ts`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/services/walletTransaction.service.ts#L85-L162) hardcodes `xlmToPhpRate = 12.5`, falls back to fabricated constants (`propBudget = ... || 34.0`, `phase1Amt = (propBudget * 0.69) || 2130.6`, `phTitle = "Phase 1: Sports Gear Procurement & Clinic Preparation"`), and assumes the oldest Horizon operation (`idx === 0`) is always `"📋 Project Escrow Created & Locked"`.
- **Fundora Remediation:** Replace heuristic transaction parsing with structured `transaction_references` recorded at the time of each NEAR contract execution (capturing the real NEAR `transaction_hash`, block timestamp, NEP-297 event name, exact `yoctoNEAR` amount, and snapshot PHP rate) cross-verified against NEAR RPC (`EXPERIMENTAL_tx_status`) and NearBlocks Testnet API.

### Issue 12: Silent Email Failure Without Delivery Verification
- **Legacy Evidence:** [`src/services/email.service.ts`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/services/email.service.ts#L1-L22) simply writes a document to the `mail` collection in Firestore (`addDoc(collection(db, "mail"), ...)`). If the Firebase Trigger Email extension is not configured or fails, no error is surfaced and users never receive status notifications. Meanwhile, registration email verification relies on Firebase Auth's built-in `sendEmailVerification` ([`auth.service.ts`](file:///C:/Users/Renz%20Jericho%20Buday/barangay-bond/src/services/auth.service.ts#L39)).
- **Fundora Remediation:** Keep Firebase Auth's native `sendEmailVerification` for account activation, and replace silent `mail` collection writes with an explicit **In-App Notification Center (`notifications` collection)** as the primary guaranteed delivery channel, supplemented by an optional backend transactional email adapter (Resend/SMTP) that logs explicit delivery status (`sent` / `failed` / `disabled_in_demo`).

## 4. NEAR Hackathon 2026 Track & Strategy Evaluation

### 4.1 Selected Track Alignment
Based on the 13 official NEAR Hackathon 2026 tracks evaluated in the Phase 1 Feasibility Audit:
- **Primary Track:** **Track 8 — Real-World Money** (Compatibility: **High**). Fundora solves a concrete, real-world public finance accountability problem (grassroots SK and Barangay project disbursements) using programmable milestone escrow, live PHP valuation, and verifiable transaction-linked receipts.
- **Secondary Track:** **Track 4 — Autonomous Business / Civic Treasury** (Compatibility: **High**). Fundora integrates an AI Procurement & Evidence Auditor agent (`auditor.fundora.testnet`) that autonomously evaluates itemized budgets against DTI SRP benchmarks, recommends inter-agency equipment borrowing, and signs on-chain audit attestations that inform human governance and smart contract execution.

### 4.2 Recreation Strategy Selection
We select **Strategy C (Hybrid Clean-Room Rebuild in `Fundora`)**:
- Preserve the proven domain workflows, UI/UX component structure, CSS design system, and step-by-step PSGC registration journey from `barangay-bond`.
- Replace the blockchain layer with a purpose-built **NEAR Rust (`near-sdk-rs`)** smart contract, replace custodial Stellar keys with **NEAR Wallet Selector**, and move Gemini AI calls to a **server-side AI Auditor & Verification API** inside the new `C:\Users\Renz Jericho Buday\Fundora` workspace.
